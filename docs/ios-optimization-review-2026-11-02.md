# iOS 优化记录（2026-11-02）

本记录来自当前源码和发布 TODO 的静态审查，尚未通过构建、模拟器或真机复现。本次修订已逐条对照源码，修正了与实现不符的描述，并补充了代码位置（行号以审查时的工作区为准）。建议优先处理照片导出失败重试和识别异常提示（均为 P0），再处理照片预览性能，然后推进照片撤销与主体选择恢复。现有免费与永久版权益边界保持不变。

## 1. 照片导出失败后的重试

**优先级：P0**

导出失败的照片会被标记为 `failed`（`PhotoBatchEditorView.swift` 约 1350 行）。之后导出数量和导出目标都会排除该状态（约 277、1295 行），因此当前代码没有重试失败照片的入口：重新点击导出会跳过这些照片；当前照片为 `failed` 时，导出按钮被禁用（约 148 行）。全部失败时不会生成结果页（仅 `successCount > 0` 时才设置 `exportResult`），也没有错误提示。`photo.failedCount` 文案已存在于 `Localizable.xcstrings`，但 Swift 代码中未引用。

`failed` 状态同时用于分析失败（约 1157 行）。当前照片为 `failed` 时，预览区显示“照片无法读取”（`photo.invalid`，约 485–487 行），这与导出失败的语义不符。目前唯一能让失败项重新处理的入口是“重新识别全部图片”（约 752 行），它会清空所有输出并重新分析整批照片，并不是针对失败项的重试。

因此，[发布 TODO](ios-launch-todo.md) 中“批量逐张报告成败，失败可重试”的勾选与当前代码不符，不应作为当前行为的证明。本次已在 TODO 中将该项改回未完成，并注明复核结论；修正实现后再重新勾选。

建议区分不可读取、分析失败和导出失败三类状态，保留失败照片的编辑数据与原因；提供“重试失败项”；部分成功时显示成功与失败数量（可复用 `photo.failedCount` 文案），全部失败时给出可操作的提示。免费用户仍每次只能导出当前一张，`PhotoProcessor.export` 中的 `prefix(1)` 处理器内限制不能放松。

验收：单张和批量分别注入全部失败、部分失败，确认提示、重试、已成功文件、取消和临时文件清理；覆盖免费和永久版权益。

## 2. 照片预览连续更新的性能

**优先级：P1**

调整强度、颜色、ASCII 等设置会通过 `onChange` 触发 `refreshPreview`（`PhotoBatchEditorView.swift` 约 198–212 行），目前没有防抖或合并。请求 ID 已阻止旧结果覆盖新画面，但 `PhotoProcessor.renderPreview` 使用 `Task.detached`（约 420–440 行），外层 `previewTask.cancel()` 不会使其停止。每次渲染还会重新读取原图、生成预览并创建 `CIContext`。连续拖动时可能产生多余工作，性能影响需实测。

建议合并短时间内的连续更新、让过期工作尽早停止，并评估复用当前图片预览及渲染资源；保留切图不显示上一张、失败可重试和预览与导出效果一致的行为。

验收：快速拖动参数、切图及离开页面时，检查最终画面、交互响应和内存；在真实 iPhone 对比优化前后的耗时与峰值内存。

## 3. 识别异常与无主体时的处理

**优先级：P0，涉及隐私体验**

视频自动识别（`VideoProcessor.swift` 的 `personDetections`、`faceDetections`、`petDetections`，约 972–1200 行）在 Vision 报错时返回空数组。照片识别（`PhotoProcessor.swift` 中人物、人脸、宠物相关函数，约 696–872 行）同样用 `try?` 吞掉错误。结果上，“确实没有主体”和“识别失败”无法区分。

无主体时的行为也需要确认。`FrameEffectProcessor.render`（`VideoProcessor.swift` 约 903–910 行）在没有自动识别结果、手动蒙版和外部蒙版时直接返回原画面。主体模式下，这等于不做处理，符合预期。背景模式下，这个返回发生在反相之前（约 934 行），因此整帧保持未遮盖。照片渲染也复用同一路径（`PhotoProcessor.render` → `FrameEffectProcessor`）。如果产品预期是“背景全部遮盖”，这就是隐私风险，因此本节提升为 P0；修复方案前需先与产品确认预期。

建议区分识别错误和正常的无检测结果，对识别失败给出明确提示，并避免静默导出。明确背景模式无主体时的预期，并检查预览和最终导出行为一致。不要将普通无主体帧一律视为错误，也不要承诺自动识别零漏检。

验收：通过可控方式模拟检测失败和无主体，覆盖主体/背景模式、手动蒙版及预览/导出；对转头、遮挡、多人进出画面进行真机检查。涉及人脸数据处理方式变化时，按仓库规则同步四语隐私政策、审核说明及文档。

## 4. 照片撤销和主体选择恢复

**优先级：P1**

照片编辑器目前没有撤销功能。视频编辑器有会话级撤销（`EditorView.swift` 的 `undoMaskEdit`，约 1316 行），可作参考。切换识别主体会调用 `analyzeAll`（`PhotoBatchEditorView.swift` 约 194 行，函数体自 1117 行起）。它会删除整批照片的所有非手动区域（约 1124–1131 行），把状态重置为待处理，并使已导出结果失效。用户对自动区域的调整会随之丢失，手动区域则保留。[发布 TODO](ios-launch-todo.md) 中也已列出照片撤销与自动识别开关恢复选择（第 250 行）。

建议为照片区域编辑（添加、删除、移动、缩放、手绘）提供撤销；评估重新识别时能否可靠对应并恢复原有的自动区域调整。无法可靠匹配时明确提示，避免静默套用错误区域。

验收：覆盖添加、删除、移动、缩放、手绘及主体开关，检查切图、重新分析、撤销和导出结果；核对四语与大字体布局。
