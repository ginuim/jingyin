# LensHide Android 技术原型验证 — 2026-11-02

## 结论与范围

已建立可构建、可安装的原生 `android/` 实验工程，验证了 YuNet CPU 人脸检测、GPU 像素化、Media3 视频导出和单张照片保存链路。当前是技术原型，不是完整安卓产品，也没有完成 ncnn、人物/猫狗检测或精细分割的性能对比。

本轮用户明确要求开始安卓试验，作为原「Android 后置」决策的本次授权；不改变 iOS 当前发布承诺，不将任何 iOS 待验项标记完成。

## 最低 Android 版本建议

原型暂定 `minSdk = 31`（Android 12）。提高 minSdk 会阻止旧系统设备安装，但它筛选的是系统 API，不是芯片性能、内存或硬件编码器。旧旗舰可能比运行较新系统的入门机更快。`compileSdk` 和 `targetSdk` 也不能代替这个性能筛选。

Google Play 要求普通手机新应用和更新自 2026-08-31 起以 Android 16 / API 36 或更高为目标；原型目前的 `targetSdk = 35` 尚不满足提交要求。上架前需升级 `compileSdk` 与 `targetSdk` 至至少 36 并完成兼容验证；这不要求将 `minSdk` 提高至 36。[Google Play 官方要求](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en)

建议先保留 API 31，实测后再决定是否值得提高到 API 33 / 34；不能仅为了排除低性能机就直接要求 Android 14/15。正式设备分级应共同检查：

1. arm64、OpenGL ES 3；模型与颜色转换的实际耗时。
2. RAM、`isLowRamDevice`、可用堆内存；这些信息不能单独预测整段导出稳定性。
3. H.264 硬件解码、编码的可用性及实际分辨率/帧率支持，不能只看 codec 名称。
4. 720p 整段导出耗时、峰值内存、持续负载后的热降频、取消耗时及最终漏遮率。

本轮设备报告只读取内存、ABI、CPU 数和 H.264 编码器能力，展示原始事实；尚未实现完整硬件解码器探测、自动性能分档或设备排除策略。模拟器没有硬件 H.264 编码器，但软件路径仍能完成导出，这是链路验证，不能据此宣称硬件路径通过。

参考：[Android uses-sdk 定义](https://developer.android.com/guide/topics/manifest/uses-sdk-element)、[MediaCodecInfo](https://developer.android.com/reference/android/media/MediaCodecInfo)。

## 环境与素材

- 本机 Apple Silicon；Android 15 / API 35 ARM64 模拟器 `Medium_Phone_API_35`。
- 模拟器报告：1 CPU、RAM 1.93 GiB、lowRam=false、heapClass 192 MiB；H.264 编码器 `c2.android.avc.encoder` 为软件编码器。
- YuNet `2023mar`，OpenCV 4.12.0 CPU、2 线程；320×320 补黑边输入，另做 640 输入照片对照。模型及许可随包附带，哈希见 `android/THIRD_PARTY.md`。
- 素材来自仓库已有婚礼合照演示视频，手工检查可见 8 张脸；照片样本为其一帧。矩阵输入为该素材循环生成，横屏 640×360 / 15fps，竖屏为中央裁切后的 360×640 / 15fps。
- 这是简单合照场景，不是运动、侧脸、小脸、遮挡或跨镜头质量评测。不能用此样本推断复杂素材召回率，也不能把模拟器速度当成低端手机跑分。
- 检测记录不上传；首轮模拟器验证时无已授权可用的安卓真机，未向 USB 设备安装内容。后续 OnePlus 3 真机尝试与结果见本文末尾。

## 结果

照片同一实例预热 3 次，再测 20 次。下表取一次固定测试记录，结果会随主机负载变化；只统计检测路径，不包括完整图片解码/缩放/保存。

| 输入 | 检出数 | 中位数 | P95 | 最大值 |
| --- | --- | --- | --- | --- |
| 320×320 | 8 / 可见 8 | 5.65 ms | 8.93 ms | 9.34 ms |
| 640×640 | 8 / 可见 8 | 20.57 ms | 41.27 ms | 55.50 ms |

短视频：2 秒输入输出约 1.958 秒，逐帧处理 48 帧、累计 384 个检测框；一次冷路径耗时 1.15 秒，检测平均 6.02 ms，效果提交平均 9.57 ms。效果提交指标包含同步低分辨率回读，但不等于 GPU 最终所有指令执行完毕时间。

六条矩阵路径全部通过，下表均为**免费路径输出前 30 秒**，每次分析 450 帧。源素材 1 分钟/3 分钟不代表已验证完整 1 分钟/3 分钟导出。

| 源时长/方向 | 声音 | 显示尺寸 | 端到端耗时 |
| --- | --- | --- | --- |
| 30 秒横屏 | 原声 | 1280×720 | 6.86 秒 |
| 30 秒横屏 | 静音 | 1280×720 | 6.24 秒 |
| 1 分钟竖屏 | 原声 | 406×720 | 4.43 秒 |
| 1 分钟竖屏 | 静音 | 406×720 | 4.24 秒 |
| 3 分钟横屏 | 原声 | 1280×720 | 6.14 秒 |
| 3 分钟横屏 | 静音 | 1280×720 | 5.97 秒 |

竖屏的编码尺寸是 720×406，带 90° 显示旋转；已按显示尺寸验收，并抽取实际成片查看，不能仅根据编码宽高判断方向错误。另用实际含 90° display matrix 的 2 秒素材验证，导出后显示方向正确且存在人脸遮盖；已查看成片抽帧。

取消测试一次记录为 23 ms（取消请求到任务完成并排空清理消息），未留下新增临时输出。损坏文件失败后重试有效。这个样本不代表所有厂商编码器都能在相同时间取消。

内存仅做诊断采样，未完成规范峰值内存测试；不能给出真机内存上限、热稳定性或电量结论。

## 检查通过的范围

- Debug APK 与仪器测试 APK 构建；arm64 与 x86_64 分包生成。arm64 APK 约 55 MiB，OpenCV 完整 native 库是主要体积来源，尚未达到正式包体目标。
- Android Lint 无 error；仍有依赖更新提示，版本固定为本轮基线，并不意味着已通过正式发布的依赖/SDK 审核。
- 三个基础仪器测试：照片检测与区域像素实际变化、短视频导出、取消/损坏素材/重试；矩阵测试一项涵盖六条导出路径；90° 旋转源素材测试一项，均已分别通过。
- 所有矩阵输出重新读取视频尺寸、显示旋转、时长及音轨存在性；静音无音轨，原声有音轨。没有进行口型同步或变音质量验收。
- 源文件刻意添加二进制 GPS `loci` atom 与 2020 年拍摄时间。输出不再包含源位置 atom，源拍摄时间不保留。发现 Android 读取器不能暴露该源 GPS 后，改用 MP4 atom 解析防止假通过。
- 对保留的竖屏成片另外用 ffprobe 检查：无源 GPS、无源 2020 年拍摄时间；Android muxer 会新生成本次导出时间和 `com.android.version`，因此**不声称输出全部 metadata 为空**。正式版如要求连生成的系统标签也去除，需更换/收口封装器。
- 已从系统选择器选图，完成 UI 内 20 次检测、显示打码结果并保存到 MediaStore 相册；检查到新 JPEG。
- 查看照片、横屏成片、竖屏成片和旋转源成片抽帧，示例人脸遮盖位置正确。这不是逐帧人工漏遮验收。
- Android 资源与 iOS catalog 新增 16 个实验版文案，四语键完整、XML/JSON 可解析；iOS 未修改 Swift 逻辑，未运行 iOS 构建，也未操作 App Store Connect。

## 补充：OnePlus 3 旧机安装试验

用户明确要求好奇性试跑旧一加，允许临时降低安装门槛，遇到不兼容不展开适配。设备为 `ONEPLUS A3000 / OnePlus3`，Android 9 / API 28，arm64，平台 `msm8996`；此时已获得 ADB 授权。

新增 `-PlabMinSdk=28` 本地构建参数，默认仍是 API 31。对设备报告中 API 29 才存在的 `isHardwareAccelerated` 添加版本保护，旧系统显示 unknown，不通过编码器名称猜测。未改变 targetSdk、付费边界或 iOS 实现。

API 28 Debug APK 和测试 APK 构建通过；检查成品 manifest 确认为 minSdk 28。执行安装失败：`Requested internal only, but not enough space`。手机 `/data` 约 53 GB，已用 52 GB，可用约 520 MB。空间检查发生在系统安装器，App 尚未启动，不能据此推断 Android 9 的运行、检测或导出兼容性。

按用户限定的试验范围停止；未删除用户文件、应用或缓存，未绕过系统存储检查。保留 API 28 试验 APK，正常默认构建恢复为 API 31。旧系统相册保存和部分媒体 API 尚未适配，此次不将 minSdk 降低视为正式支持 Android 9。

### 用户清理空间后的重试

用户报告剩余 1.32 GB，ADB 实际显示 `/data` 约 1.2 GB。原 API 28 APK 安装成功，MainActivity 启动通过。设备报告 RAM 5.60 GiB、4 CPU、heapClass 256 MiB。

- 照片仪器测试通过：同一 8 人合照，预热后测量 20 次，320 输入记录检出 8 张脸；中位数 19.37 ms、P95 21.66 ms。640 输入检出 8 张脸，中位数 67.81 ms、P95 72.94 ms。检测区域实际像素变化断言通过。
- 第一次视频尝试因 Android 9 的 `MediaMetadataRetriever` 不能转换成 `AutoCloseable` 而失败，发生在读取元信息阶段，尚未编码。将生产路径与测试中的 `.use` 改为 `try/finally release()` 兼容封装后重试通过；没有扩展成完整旧系统适配。
- 2 秒横屏静音样本逐帧处理 48 帧、累计 384 张脸，输出 H.264 1280×720，耗时 2.79 秒；检测平均 20.86 ms，效果提交平均 23.68 ms。编码器为 `OMX.qcom.video.encoder.avc`。Android 9 无标准硬件加速布尔查询 API，不把名称当成正式能力证明。
- 取回成片，用 ffprobe 核对为 H.264、1280×720、容器时长 2 秒；检查抽帧，8 张脸的像素化位置正确。只有短、简单合照样本，不代表 30 秒/1 分钟/3 分钟、热稳定性或复杂漏遮验收通过。
- 更新后的 API 28 APK 已安装并保留在手机；正常 API 31 默认构建重新生成，构建与 Lint 通过。此次不改 minSdk 默认决策或 targetSdk，不操作 iOS / App Store Connect。
- 改动文件：`VideoExporter.kt` 增加兼容释放函数；`PipelineTest.kt` / `MatrixTest.kt` 复用它；同步此记录及 Android README。保留测试日志、成片与报告于被 Git 忽略的 `android/app/build/reports/oneplus3/`。
